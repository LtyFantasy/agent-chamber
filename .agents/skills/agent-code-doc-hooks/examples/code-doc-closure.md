# 通用代码-文档 Hook 闭环示例

本例借用“订单结算”概念演示结构，不规定真实项目必须使用这些目录、语言或文档工具。落地时必须替换为当前工程的权威文档定位符和真实代码归属。

## 代码侧：使用本地功能文档

~~~typescript
/**
 * =============================================================================
 * AGENT-CODE-HOOK | 修改本文件前必读
 * =============================================================================
 * [功能概念]
 *   - 订单结算与幂等
 *
 * [代码职责]
 *   - 编排支付、库存和结算事件的提交边界
 *
 * [权威文档]
 *   - 主文档: docs/orders/settlement.md § 原子提交 — 事务边界与外部结果合同
 *
 * [关键不变量]
 *   - 支付确认与库存扣减必须同时提交或同时不发生。
 *   - 相同幂等键重试时返回既有结果，不得重复产生副作用。
 *
 * [关联代码]
 *   - src/orders/order-repository.ts#commitSettlement — 原子持久化
 *   - test/orders/settlement.integration.test.ts — 回滚与重试证明
 *
 * [持久踩坑]
 *   - ORDER-004(幽灵事件): commit 前发布事件会产生无法回滚的外部观察。
 *     事件必须暂存并在 commit 后发布。详情: docs/orders/settlement.md § Pitfall ORDER-004
 *
 * [修改检查]
 *   □ 已读 [权威文档]，确认修改符合设计意图
 *   □ 已核对 [关键不变量] 与 [关联代码] 的影响面
 *   □ 行为、合同、不变量或归属变化时，同步更新文档侧 AGENT-DOC-HOOK
 *   □ 如需修复缺陷，先完成根因分析、影响面评估、风险匹配测试与验证
 * =============================================================================
 */
~~~

以上路径只是示例，不是规定目录。

## 代码侧：使用托管知识库

同一个概念也可以使用知识系统的稳定路由：

~~~text
[权威文档]
- 知识路由“订单结算与幂等” -> “原子提交”
  （稳定文档键: orders-settlement）
~~~

即使系统需要不透明 ID，也要同时保留可读的概念、文档名称和章节，让未来 Agent 知道为什么要打开它。

## 文档侧：反向代码地图

在对应功能文档中提供反向 Hook：

~~~markdown
> **AGENT-DOC-HOOK | 代码归属与验证入口**
>
> **[功能概念]**
> - 订单结算与幂等
>
> **[实现入口]**
> - `src/orders/settle-order.ts#settleOrder` — 流程入口与编排
> - `src/orders/order-repository.ts#commitSettlement` — 原子持久化
> - `src/orders/settlement-events.ts#stageSettlementEvent` — 提交后事件
>
> **[验证入口]**
> - `test/orders/settlement.integration.test.ts` — 回滚、重试和无重复副作用
>
> **[同步检查]**
> - 代码归属或本文合同变化时，同步更新本映射和对应代码侧
>   `AGENT-CODE-HOOK`。
~~~

## 不放进 Hook 的内容

- 完整结算法则；
- 所有调用方和辅助函数；
- 事故从发现到修复的完整时间线；
- 临时调试命令；
- 与本概念无关的全项目开发规则。

这些信息应留在权威功能文档、持久证据记录或工程通用规范中。Hook 只负责在未来会话触及代码时，注入正确的阅读路径与约束。
